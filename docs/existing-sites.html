Workflow · Migrations

Migrate an existing site to Nift.

nift init --migration creates a normal Nift project plus an agent-ready migration playbook. Nift provides the rails; the agent (or you) understands the source framework. Parity comes before cleanup.

Start a migration in one command.

nift init --migration
Then give the working copy to a coding agent - or ask the agent to run that command itself - and follow the generated playbook.

Run it yourself, or let your agent run it

Either workflow is valid:

# You run it, then hand the project to an agent:
cd <migration-project>
nift init --migration

Or give the agent the repository and let it initialize in its own environment:

> Run `nift init --migration` in this project.
> Read MIGRATION.md, HANDOVER.md and the Nift section of AGENTS.md, then migrate the site to Nift.
> Preserve route, content and behavioural parity, work through the migration checkpoints,
> keep HANDOVER.md current, and stop/report if the migration appears to require a change
> to Nift itself.

What Nift creates

  • MIGRATION.md - the migration playbook and parity gates.
  • HANDOVER.md - current progress, decisions, blockers and the exact next action.
  • AGENTS.md - project-local instructions for coding agents; Nift safely manages only its own marked section.
  • investigation/ - evidence, reproductions, route inventories, benchmarks and compatibility work.
  • Canonical MIGRATION.md
  • Canonical HANDOVER.md

How the migration works

  1. Baseline - reproduce the source revision and build before changing anything.
  2. Inventory - content, routes, layouts, components, shortcodes, assets, data, frontmatter, redirects.
  3. Parity fixtures - route/generated-file inventories and a known-divergence ledger.
  4. Migrate - shared shells/templates first, then authored content with reconciled counts.
  5. Verify - route-set and file-set comparison, content parity, incremental-vs-full equivalence.
  6. Benchmark - fair full/warm/targeted builds plus peak RSS, with compatibility-stage cost separated.
  7. Clean checkout - a fresh clone must build without hidden local state.
  8. Handover - exact revisions, known divergences, remaining work and a maintenance recommendation.

Existing MIGRATION.md/HANDOVER.md files are never silently overwritten: the default policy stops with a list of conflicts, and --migration-existing=keep, append, or replace make the behaviour explicit.

Parity-first migration

Preserve route, content and behavioural parity unless divergence is explicitly approved, and maintain an explicit known-divergence list. A faithful migration may initially retain architectural baggage from the source generator; do not clean up too early, and prefer faithful compatibility over speculative rewrites.

Route preservation

Route preservation is a first-class migration invariant. Compare the authoritative route set, detect missing and extra routes, preserve redirect behaviour, and account for generated/index routes.

Foreign compatibility stages

Migration does not require Nift to reproduce every source generator’s semantics natively. External renderers and adapters are legitimate when parity requires them - for example Goldmark, Chroma, an MDX rendering stage, or source-specific shortcode adapters - without being bundled by Nift.

Dependency correctness

Imported includes, assets, data, shared templates, and generated dependencies must become correct Nift dependencies where appropriate.

Incremental correctness

Verify single-page edits, shared-template edits, asset/data changes, and targeted builds, plus incremental-vs-full equivalence. A migration that only passes a full clean build is insufficient evidence.

Verification

Use route checks, file-set checks, content checks, browser checks, and keyboard/runtime checks where relevant. No migration is complete while unexplained differences remain.

Benchmarking

Measure fairly on the same machine with the same corpus: the source build, Nift full/warm/targeted builds where relevant, and peak RSS. Separate and report compatibility-stage renderer cost honestly.

Clean clone

A migration is not finished until a fresh checkout builds and passes parity checks without hidden local state or absolute developer-machine paths.

Handover

MIGRATION.md holds methodology and parity requirements; HANDOVER.md holds current operational state and the exact next action; AGENTS.md merges Nift’s managed migration block into project instructions; investigation/ holds baseline evidence and findings.

When Nift itself seems to need a change

If a migration exposes a gap that looks like Nift core, stop and isolate the requirement with a narrow reproduction. Do not casually modify Nift core from inside the site migration; report the requirement separately.

What comes after migration

A faithful migration achieves source parity first. Once the constraints are understood, a later native-Nift evolution can simplify the architecture - but keep a compatibility stage until parity is proven and the simplification is explicitly authorized.

The canonical MIGRATION.md

nift init --migration writes this file to the project root, byte-for-byte:

The canonical MIGRATION.md

# MIGRATION.md

A migration workbook for converting an existing site to Nift.

This project was created with `nift init --migration`: a normal Nift project
with an agent-ready migration playbook. It is **not** an automatic converter.
Nift provides the rails; the human or coding agent understands the source
framework. Parity comes before cleanup.

Read this file first. Read `HANDOVER.md` second and keep it current after
meaningful checkpoints. `AGENTS.md` (created or augmented by init) points
agents here.

## Operating contract

These rules are the migration contract. Do not violate them without explicit
authorization.

- Preserve route, content and behavioural parity unless divergence is
  explicitly approved.
- Do not modify Nift itself to solve source-project compatibility problems
  without stopping and reporting the requirement first.
- Commit at meaningful migration checkpoints.
- Maintain an explicit known-divergence list.
- Do not classify the migration as complete while unexplained differences
  remain.
- Prefer faithful compatibility stages over speculative rewrites.
- Do not optimize or redesign before the faithful baseline is established.
- Do not destroy the upstream/reference implementation while it is still
  needed for comparison.
- Record exact source and migration revisions.
- Keep `HANDOVER.md` current after meaningful checkpoints.

## Workflow

### Phase 1 - Understand the source project

Before changing anything, establish and record:

- source framework/generator and version;
- upstream repository and exact source revision/commit;
- source build command (and development command where relevant);
- deployment architecture;
- authored content inventory;
- templates/layouts inventory;
- components/shortcodes/render hooks inventory;
- static asset inventory;
- generated/index/listing pages;
- redirects;
- data files and schemas/taxonomies/frontmatter conventions;
- special rendering behaviour;
- the authoritative route set;
- upstream build time and peak memory.

Invariant: **DO NOT START MIGRATION UNTIL THE SOURCE BASELINE CAN BE
REPRODUCED.**

### Phase 2 - Establish parity fixtures

Build appropriate reference evidence before broad migration. Use proportional
fixtures; do not mandate browser testing where it is irrelevant. Candidate
fixtures:

- route inventory;
- generated-file inventory;
- representative browser captures;
- content checks;
- navigation checks;
- keyboard/runtime behaviour where relevant;
- mobile/desktop viewport coverage;
- a known-divergence ledger.

### Phase 3 - Establish the initial Nift structure

Set up:

- project initialization;
- tracking;
- source/output layout;
- templates;
- dependencies;
- schemas/taxonomies where appropriate;
- migration checkpoint structure.

Do not prematurely redesign the source architecture.

### Phase 4 - Migrate shared shells/templates first

Identify and recover the largest common structure first:

- common page shells;
- shared heads;
- headers/footers/navigation;
- layouts;
- repeated structural components.

### Phase 5 - Migrate authored content

Reconcile explicit corpus accounting:

- expected authored inputs;
- converted inputs;
- remaining inputs;
- generated/listing layouts;
- route counts.

Counts must be reconciled rather than guessed.

### Phase 6 - Source-specific compatibility

**MIGRATION SUPPORT DOES NOT MEAN NIFT MUST NATIVELY REIMPLEMENT EVERY SOURCE
GENERATOR'S SEMANTICS.** Faithful compatibility stages are legitimate. For
example, a Hugo source may require Goldmark or Chroma, MDX may use an
external/package rendering stage, and special shortcodes may need adapters.

Rule: **Prefer faithful compatibility over semantic rewrites unless the
migration goal explicitly permits behavioural changes.** And: **DO NOT MODIFY
NIFT CORE TO SOLVE A SOURCE-PROJECT COMPATIBILITY GAP WITHOUT STOPPING AND
REPORTING THE REQUIREMENT FIRST.**

### Phase 7 - Route/content/rendered parity

Require:

- an authoritative route-set comparison;
- missing and extra route detection;
- generated-file-set comparison where meaningful;
- content/render parity checks;
- explicit divergence classification.

No migration is complete while unexplained differences remain.

### Phase 8 - Incremental correctness

Verify, as appropriate for the project:

- single-page edits;
- shared-template edits;
- asset changes;
- data changes;
- dependencies;
- targeted builds;
- incremental-vs-full equivalence.

A migration that only passes a full clean build is insufficient evidence.

### Phase 9 - Benchmark

Record proportionally:

- source baseline build time;
- Nift clean/full build time;
- warm/full and targeted/single-page builds where useful;
- peak RSS;
- environment/hardware;
- measurement methodology.

Do not cherry-pick. Do not hide compatibility-stage cost. If an external
renderer exists, measure and report its cost separately where useful.

### Phase 10 - Clean-checkout verification

Before completion verify on a fresh checkout:

- fresh clone;
- dependency acquisition;
- build from scratch;
- route/content checks;
- no reliance on untracked local state;
- no absolute developer-machine paths.

### Phase 11 - Handover / final report

Produce a final report containing at least:

- source revision;
- migration revision;
- route counts;
- content counts;
- known divergences;
- compatibility stages;
- build measurements;
- memory measurements;
- clean-checkout result;
- remaining work;
- maintenance recommendation.

## Document roles

- `MIGRATION.md` - methodology, baseline, migration plan, parity
  requirements, checkpoints, migration-specific evidence/state.
- `HANDOVER.md` - current operational state, completed work, current blocker,
  exact commands, important decisions, exact next action.
- `AGENTS.md` - project instructions (Nift's migration block is managed and
  safe to augment).
- `investigation/` - baseline evidence, reproductions, audit notes, route
  inventories, browser-matrix metadata, benchmark data, compatibility findings.

## What comes after migration

A faithful migration achieves source parity first. Once the constraints are
understood, a subsequent native-Nift evolution may simplify the architecture -
but do not strip away a compatibility stage until parity is proven and the
simplification is explicitly authorized.

You do not have to migrate everything at once

If you are keeping an existing site and want a lighter first step, you can also add Nift without a full migration. Keep the site’s HTML, CSS, JavaScript, assets and runtime architecture, and use Nift to extract repeated structure - shared heads, headers/footers/navigation, and repeated structural components - into templates and a fast tracked build layer.

index.html
about.html
services.html
work.html
contact.html

Every page repeats:
  <!doctype html>
  <head>...</head>
  header / navigation
  footer
  CSS / JS references

Extract the repetition, use @content/@input/@path to compose it, and keep the parts that are already working. This incremental-adoption path does not require a rewrite and does not translate the site into a different component model.
